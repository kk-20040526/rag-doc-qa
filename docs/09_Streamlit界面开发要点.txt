Streamlit 的核心机制是"脚本即应用"：整个 Python 文件就是页面，从上到下执行一遍渲染出界面。任何一次交互（点按钮、改输入框）都会让脚本重跑一遍，这是理解它所有行为的起点。

重跑带来一个重要问题：耗时对象不能每次重建。加载模型、建索引、连数据库这些操作如果写在顶层，用户每点一次按钮就重做一次，页面会卡到不可用。解决办法是两个缓存装饰器：cache_data 用于缓存可序列化的数据（比如读进来的文档列表），cache_resource 用于缓存不可序列化的全局资源（比如模型、数据库连接、检索器实例）。本项目用 cache_resource 缓存 BM25 知识库和 ES 连接，所以只有第一次构建，之后复用。

跨交互保存状态用 session_state。它不是持久化存储，只活在当前会话里，适合放"用户上次搜了什么""是否已登录"这类东西。注意缓存对象本身不要放可变状态，否则多个会话会互相污染。

布局上，侧边栏用 st.sidebar 承载全局设置（模式切换、索引管理），主区域放结果。常用组件包括 st.radio（单选）、st.text_input（输入）、st.button（按钮，可设 type 为 primary 突出主操作）、st.expander（可折叠面板，展示检索片段特别合适）、st.spinner（加载态）、st.success / st.info / st.error（三种语义提示）。

启动方式是在项目目录执行 streamlit run 主程序文件，默认端口 8501，浏览器打开 localhost:8501。部署或远程访问时用 headless 模式（不自动开浏览器）并指定 server.address。

实践中的四个坑。第一，缓存里放了大对象又改了它的内容，第二次读到的还是旧值，因为缓存按参数哈希命中。第二，cache_resource 的函数如果在不同会话里传入不同参数，会各自建一份，内存翻倍。第三，按钮返回值只在被点击那一次为真，不能把它存进变量下次再用。第四，异常会直接把错误栈打到页面上，演示前必须把每个分支都手动点一遍，尤其是"服务没起来"的分支。
