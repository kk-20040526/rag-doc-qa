本项目是一个自训练的自然场景光学字符识别系统，采用"检测 + 识别"两阶段方案：DBNet 负责找出文字行的位置，透视校正把倾斜的文字行摆正，PP-OCRv3 的识别模块（SVTR_LCNet：骨干 MobileNetV1Enhance + 颈部 SVTR + 头部 MultiHead）负责把文字读出来，三段串联成端到端推理引擎。

检测模型的骨干是 PPLCNetV3，颈部是 RSEFPN，头部是 DBHead，损失用 DBLoss。这里有个容易混淆的点：PPLCNetV3 正是 PP-OCRv4 检测模型的骨干网络，所以预训练权重取自官方 ch_PP-OCRv4_det_train，模型名与权重目录名指同一件事。

识别模型是 PP-OCRv3，骨干 MobileNetV1Enhance，颈部 SVTR，头部 MultiHead（训练时用 SAR 辅助头，推理时只走 CTC 分支），输入尺寸 48×320，解码用 CTCLabelDecode。

训练用 PaddleOCR 官方入口微调，不是自己写训练循环：先执行 tools/train.py 配 configs/det_train.yml，再配 configs/rec_train.yml，两段由脚本串联。检测配置为 Adam、学习率 1e-3、Cosine 衰减、batch 8、1 个 epoch；识别配置为 batch 48、1 个 epoch，均从官方预训练权重热启动。数据是 8000 张街景招牌图像，自建检测与识别数据集。

效果上，800 张验证集的对比是：检测 F1 从 0.487 提升到 0.557，端到端 F1 从 0.303 提升到 0.328，识别整句准确率从 0.736 变化到 0.727，识别 CER 从 0.119 到 0.121。检测提升明显，识别略有波动，原因是 CPU 环境下识别只训了 1 个 epoch（约 5.3 小时），数据量与轮数都不足；检测训练约 3.4 小时。这是算力约束下的取舍，也是后续改进方向。

工程细节有三条值得讲。第一，推理直接用动态图加载 .pdparams，不走 paddle.jit.save 导出，因为 Paddle 2.6.2 CPU 版对 PaddleOCR 的自定义 backbone/neck 结构导出会缺权重文件。第二，中文路径不兼容 cv2.imread，统一改为 np.fromfile 加 imdecode、imencode 加 tofile。第三，检测出的四点框用 getPerspectiveTransform 加 warpPerspective 做透视校正，竖排文字自动旋转 90 度，识别结果按从上到下、从左到右排序。

部署形态是 FastAPI 本地推理后端加微信小程序前端。接口有两个：GET /health 做健康检查，POST /ocr 接收一张图片，返回每个文字行的四点坐标、文本和置信度，以及一张叠加了绿色文字框的标注图。小程序拍照上传后即可看到识别结果，数据不出本机。
