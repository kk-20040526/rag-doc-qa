qwen-agent 是通义千问团队开源的智能体框架，定位是把"大模型 + 工具调用"这套流程标准化。它的核心抽象是 Assistant：一个带系统提示词、带工具列表的智能体，你给它消息列表，它自己决定要不要调工具、调哪个、拿到结果后怎么继续。

Assistant 的三个关键参数。llm 是模型配置字典，包含 model、api_key、base_url 等。system_message 是行为约束，决定它扮演什么角色。function_list 是工具清单，里面既可以放自定义工具，也可以放框架内置的工具。

工具的调用机制是函数调用（function calling）。框架把每个工具的描述和参数结构一起交给模型，模型判断需要时输出一个结构化的调用请求，框架负责执行、把结果回填成工具消息，再让模型继续。这个循环会一直跑到模型认为可以给最终答案为止，所以一个提问可能触发多次工具调用。

Retrieval 是框架内置的检索工具，构造时传入配置字典，用 docs 字段把片段列表交给它，用 method 指定检索算法（bm25 走内存稀疏检索）。调用时传一个查询字符串，它返回命中的片段。它的价值在于"零依赖"：不装向量库、不要嵌入模型，几百到一千段文档直接内存检索，启动即用。

和 LangChain 相比，qwen-agent 更聚焦在"智能体 + 工具"这一层，抽象层级更浅，适合做教学演示和轻量应用；LangChain 的生态更宽（各种 loader、vectorstore、memory），但依赖更重、版本变动更频繁。

本项目对两种检索方案的分工很明确：小文档方案用框架内置的 Retrieval（BM25）+ Assistant 自动编排；海量文档方案自己写了一个 ESRetrieval 类，绕过框架直接调 Elasticsearch 客户端，检索这一步自己控制、自己排序、自己展示得分。这样既有"框架帮我编排"的路径，也有"我自己实现检索器"的路径，便于对比。

补充一句工程经验：Assistant 的 function_list 里放检索工具时，模型有可能选择"不检索直接答"。要让它稳定地先检索，系统提示词里必须明确要求"必须先检索文档再回答"，否则行为不稳定。
